홈 더미 사이트 보안 실습실 무차별 대입 DB 관리 방어 가이드 암호화

🔐 암호화 가이드 — 해시 · 대칭키 · 공개키

SQL 인젝션을 막아도 저장된 데이터 그 자체를 지키려면 암호화가 필요합니다. 비밀번호는 어떻게 저장해야 하고, 데이터는 어떻게 암호화하며, 인터넷에서는 어떻게 안전하게 주고받는지를 해시 · 대칭키 · 공개키 세 가지 축으로 정리했습니다.

목차
1. 인코딩 ≠ 암호화 ≠ 해시 2. 해시 (단방향) 3. 해시로 비밀번호 저장하기 4. 대칭키 암호화 5. 공개키(비대칭) 암호화 6. 전자서명 7. 하이브리드 (HTTPS/TLS) 8. 한눈에 비교 9. SQLi와의 연결고리 10. 체크리스트

1. 인코딩 ≠ 암호화 ≠ 해시 — 먼저 구분하기

셋 다 데이터를 "알아보기 어렵게" 바꾸지만 목적과 되돌릴 수 있는지가 전혀 다릅니다. 가장 많이 혼동하는 지점이라 먼저 정리합니다.

🔄 인코딩 (Encoding)

Base64·URL 인코딩처럼 형식 변환일 뿐. 키가 필요 없고 누구나 되돌립니다. 보안 기능이 아닙니다.

🔐 암호화 (Encryption)

키가 있어야 원문으로 되돌릴 수 있는 양방향 변환. 비밀을 "잠갔다 다시 열기" 위한 것. (대칭키·공개키)

#️⃣ 해시 (Hashing)

원문으로 되돌릴 수 없는 단방향 지문. 비밀번호 저장·무결성 검증에 사용. 키 개념이 없음.

🧩
핵심 질문 하나로 구분됩니다: "되돌릴 수 있는가?" — 인코딩은 키 없이 되돌림, 암호화는 키로 되돌림, 해시는 되돌릴 수 없음.

2. 해시 (단방향 암호화) 비밀번호 저장 필수

해시 함수는 임의 길이의 입력을 고정 길이의 값으로 바꾸는 단방향 함수입니다. 같은 입력은 항상 같은 결과를 내지만, 결과만 보고 원문을 역산할 수 없습니다. 그래서 "암호화(복호화 가능)"라기보다 지문(fingerprint)에 가깝습니다.

SHA-256("hello")   → 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
SHA-256("hellp")   → 7f1d... // 한 글자만 바뀌어도 완전히 달라짐 (눈사태 효과)

해시의 4가지 성질

  • 결정적 — 같은 입력 → 항상 같은 해시
  • 단방향 — 해시 → 원문 복원 불가
  • 눈사태 효과 — 입력이 조금만 달라져도 결과가 완전히 달라짐
  • 충돌 저항성 — 서로 다른 두 입력이 같은 해시를 갖기 매우 어려움

❌ 쓰면 안 되는 해시

  • MD5 — 충돌 발견됨, 깨짐
  • SHA-1 — 충돌 발견됨, 폐기 권고
  • 비밀번호에 일반 SHA-256 단독 — 너무 빨라 무차별 대입에 취약

✅ 권장

  • 무결성 검증: SHA-256 / SHA-3
  • 비밀번호 저장: bcrypt · scrypt · Argon2 (느리게 설계된 전용 해시)
  • 메시지 인증: HMAC-SHA256
💡
해시는 어디에 쓰나요? ① 비밀번호 저장(다음 장) ② 파일/다운로드 무결성 검증(받은 파일 해시가 공개된 해시와 같은지) ③ 블록체인·디지털 서명의 기반.

3. 해시로 비밀번호를 안전하게 저장하기

이 사이트의 더미 DB는 피해를 보여주려 비밀번호를 평문으로 저장합니다. 실무에서는 절대 그러면 안 됩니다. 비밀번호는 해시해서 저장하고, 로그인 시 입력값을 같은 방식으로 해시해 해시끼리 비교합니다.

-- 평문 저장 (이 더미 사이트 — 유출되면 즉시 전 계정 노출)
INSERT INTO users(username, password) VALUES('admin', 'admin1234');

-- 해시 + 솔트 저장 (실무)
INSERT INTO users(username, password_hash) VALUES('admin', '$argon2id$v=19$m=65536,t=3,p=4$...');

솔트(salt)와 페퍼(pepper)

  • 솔트 — 사용자마다 다른 무작위 값을 비밀번호에 붙여 해시. 같은 비밀번호라도 해시가 달라져 레인보우 테이블(미리 계산된 해시 사전) 공격을 무력화합니다. 솔트는 해시와 함께 저장해도 됩니다.
  • 페퍼 — 모든 사용자 공통의 비밀값. DB가 아닌 앱 설정/HSM에 분리 보관해, DB만 털려도 추가 방어막이 됩니다.
  • 느린 해시 — bcrypt/argon2는 일부러 계산을 느리게 해 초당 시도 횟수를 줄입니다. (무차별 대입 비용 ↑)

언어별 예시

✅ Node.js — bcrypt

import bcrypt from 'bcrypt';

// 저장 시 (솔트 자동 생성·내장)
const hash = await bcrypt.hash(pw, 12);

// 로그인 시 검증
const ok = await bcrypt.compare(input, hash);

✅ Python — argon2

from argon2 import PasswordHasher
ph = PasswordHasher()

hash = ph.hash(pw)        # 저장
ph.verify(hash, input)    # 검증(틀리면 예외)

✅ PHP — password_hash

$hash = password_hash($pw, PASSWORD_ARGON2ID);
if (password_verify($input, $hash)) { /* OK */ }

✅ Java — Spring Security

var enc = new BCryptPasswordEncoder(12);
String hash = enc.encode(pw);
boolean ok = enc.matches(input, hash);
🚧
하지 말 것: 비밀번호를 평문/MD5/SHA-1로 저장, 직접 만든 해시 알고리즘 사용, 솔트 없이 SHA-256만 사용. 할 것: 검증된 라이브러리(bcrypt/argon2)를 그대로 쓰기 — 솔트·반복은 라이브러리가 알아서 처리합니다.

4. 대칭키 암호화 (Symmetric) 빠름

대칭키 암호화는 하나의 같은 키로 암호화도 하고 복호화도 합니다. 마치 같은 열쇠로 잠그고 여는 자물쇠와 같습니다. 연산이 매우 빠르고 큰 데이터를 효율적으로 처리해, 실제 데이터 본문 암호화에 쓰입니다.

대표 알고리즘

  • AES (AES-256-GCM 권장) — 현재 사실상 표준. GCM 모드는 암호화 + 무결성을 함께 제공.
  • ChaCha20-Poly1305 — 모바일 등에서 빠른 대안.
  • DES / 3DES — 구식, 사용 금지.

✅ Node.js — AES-256-GCM

import crypto from 'node:crypto';
const iv = crypto.randomBytes(12);
const c = crypto.createCipheriv('aes-256-gcm', key, iv);
const enc = Buffer.concat([c.update(text,'utf8'), c.final()]);
const tag = c.getAuthTag();  // 무결성 태그

👎 약점 — 키 배송 문제

  • 키 하나를 주고받는 사람 모두가 알아야 함
  • 그 키를 어떻게 안전하게 전달하지? → 네트워크로 보내면 가로채일 수 있음
  • 사람이 N명이면 키 관리가 폭증

바로 이 "키를 어떻게 안전하게 나눠 갖지?" 문제를 푸는 것이 다음의 공개키 암호화입니다.

5. 공개키(비대칭) 암호화 (Asymmetric) 키 배송 해결

공개키 암호화는 수학적으로 짝을 이루는 두 개의 키를 씁니다 — 누구에게나 공개하는 공개키(public key)와 나만 갖는 개인키(private key). 공개키로 잠그면 개인키로만 열리고, 그 반대도 성립합니다. 덕분에 키를 미리 안전하게 나눠 갖지 않아도 비밀 통신을 시작할 수 있습니다.

📮
비유: 공개키는 누구나 우편물을 넣을 수 있는 "우체통 투입구", 개인키는 "우체통 열쇠"입니다. 아무나 편지를 넣을(암호화) 수 있지만, 꺼내(복호화) 읽는 건 열쇠를 가진 나뿐입니다.

대표 알고리즘

  • RSA — 큰 소수의 곱을 인수분해하기 어렵다는 점을 이용 (2048비트 이상 권장).
  • ECC (타원곡선) — 더 짧은 키로 같은 안전성. 모바일·TLS에서 선호.
  • Diffie-Hellman / ECDH — 키 자체를 직접 보내지 않고 공유 비밀을 합의하는 키 교환.

✅ 키 쌍 생성 (Node.js)

const { publicKey, privateKey } =
  crypto.generateKeyPairSync('rsa', { modulusLength: 2048 });

  • 대칭키보다 훨씬 느림 → 큰 데이터엔 부적합

7. 하이브리드 — HTTPS/TLS는 셋을 다 쓴다

현실의 보안 통신은 세 가지를 조합합니다. 공개키로 대칭키를 안전하게 교환하고, 실제 데이터는 빠른 대칭키로 암호화하며, 서버 신원은 전자서명(인증서)으로 확인합니다. 우리가 매일 쓰는 HTTPS가 바로 이 방식입니다.

-- TLS 핸드셰이크(간략화)
1. 브라우저 ──▶ 서버: 인증서 요청
2. 서버 ──▶ 브라우저: 인증서(서버 공개키 + CA 전자서명)
3. 브라우저: 서명 검증 ✅ → 임시 대칭키 생성 → 서버 공개키로 암호화해 전송
4. 서버: 개인키로 복호화 → 이제 둘만 아는 대칭키 확보
5. 이후 모든 통신: 빠른 대칭키(AES)로 암호화

9. SQL 인젝션과의 연결고리

암호화는 SQLi의 최후 방어선입니다. 인젝션·무차별 대입을 모두 막아도, 만에 하나 DB가 통째로 유출됐을 때 피해 크기를 결정하는 것이 암호화입니다.

❌ 평문 저장 DB가 유출되면

SELECT username, password FROM users;
admin   | admin1234   // 즉시 로그인 가능
kim     | qwerty!     // 타 사이트 재사용까지 위험

✅ 해시 저장 DB가 유출되면

SELECT username, password_hash FROM users;
admin | $argon2id$...  // 원문 알 수 없음
kim   | $argon2id$...  // 크랙에 막대한 비용
  • 비밀번호 → 해시(Argon2/bcrypt) + 솔트로 저장
  • 주민번호·카드번호 등 민감정보 → 대칭키(AES-256-GCM)로 암호화 저장, 키는 분리 보관
  • 전송 구간 → HTTPS(TLS)로 보호

10. 최종 체크리스트

  • ✅ 비밀번호는 Argon2 / bcrypt / scrypt + 솔트로 저장 (평문·MD5·SHA1 금지)
  • ✅ 민감정보는 AES-256-GCM 등 대칭키로 암호화, 키는 코드/DB와 분리 보관
  • ✅ 키 교환·신원확인엔 공개키(RSA/ECC)와 전자서명
  • ✅ 모든 통신은 HTTPS(TLS) — 해시·대칭·공개키의 하이브리드
  • ✅ 검증된 라이브러리만 사용, 직접 만든 암호 알고리즘 금지
  • ✅ 무결성이 필요하면 HMAC 또는 인증 암호화(GCM) 사용
