1. SQL 인젝션이란

SQL 인젝션(SQL Injection)은 애플리케이션이 사용자 입력값을 충분히 검증·분리하지 않고 SQL 질의문에 문자열로 직접 이어 붙일 때 발생합니다. 공격자는 입력값에 따옴표('), 주석(--), UNION 같은 SQL 문법을 섞어 넣어, 개발자가 의도한 것과 다른 쿼리를 데이터베이스에서 실행시킵니다.

🧩
핵심은 "데이터"로 다뤄야 할 입력이 "코드(SQL 문법)"로 해석되는 것입니다. 모든 방어 기법은 결국 입력을 코드가 아닌 값으로만 다루게 만드는 것으로 귀결됩니다.

2. 왜 위험한가

  • 인증 우회 — 비밀번호 없이 관리자 계정으로 로그인
  • 정보 유출 — 회원 전체의 아이디·비밀번호·개인정보 탈취 (이 사이트의 더미 DB에서 직접 확인 가능)
  • 데이터 변조·삭제 — UPDATE/DELETE/DROP으로 데이터 파괴
  • 권한 상승·내부 침투 — DB 계정 권한에 따라 서버 명령 실행, 파일 접근까지 이어질 수 있음

OWASP Top 10에서 인젝션은 수년째 최상위권 취약점입니다. 한 줄의 잘못된 쿼리가 서비스 전체를 위협합니다.

3. 공격 원리 — 쿼리는 이렇게 변형된다

로그인 쿼리를 문자열로 결합하는 취약한 코드를 보겠습니다.

const sql = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'";

여기에 아이디로 admin' -- 를 입력하면, 최종 쿼리는 다음과 같이 바뀝니다.

SELECT * FROM users WHERE username = 'admin' --' AND password = '...'

입력 속 ' 가 문자열을 닫아버리고, -- 뒤는 SQL 주석이 되어 AND password = '...' 비밀번호 검사가 통째로 사라집니다. 결국 DB는 이렇게 해석합니다: 

SELECT * FROM users WHERE username = 'admin'   -- 나머지는 주석 처리됨

비밀번호를 몰라도 admin 행이 반환되어 로그인에 성공합니다. 이것이 인증 우회의 원리입니다.

입력값
admin' --
→
따옴표로 문자열 종료
'
→
주석으로 뒷부분 무력화
--
→
비밀번호 검사 제거
→ 인증 우회

4. 대표 공격 유형

① 인증 우회 (Tautology)

항상 참인 조건을 주입해 WHERE 절을 무력화합니다. ' OR 1=1 --, admin' -- 등.

② UNION 기반 추출

원래 쿼리 결과에 UNION SELECT로 다른 테이블의 데이터를 이어 붙여 한 번에 끌어냅니다. 컬럼 개수·타입을 맞추는 것이 관건입니다.

검색어: %' UNION SELECT id, username, password, email FROM users -- 
→ 공지 목록 대신 회원 계정·비밀번호가 함께 반환됨

③ 불리언 기반 블라인드

결과가 직접 안 보일 때, 참/거짓에 따른 응답 차이로 데이터를 한 비트씩 알아냅니다. ... AND SUBSTR(password,1,1)='a'.

④ 시간 기반 블라인드

응답 내용이 전혀 없을 때, 조건이 참이면 지연되도록 만들어 시간 차이로 추론합니다. ... AND SLEEP(5), WAITFOR DELAY.

⑤ 오류 기반

일부러 DB 오류를 유발하고, 오류 메시지에 데이터가 노출되게 만듭니다. → 상세 오류 메시지를 사용자에게 보여주지 않는 것이 방어.

⑥ 스택 쿼리

; DROP TABLE users -- 처럼 여러 문장을 한 번에 실행. 드라이버/DB 설정에 따라 차단되기도 하지만, 허용되면 치명적입니다.

5. 방어① 파라미터화 쿼리 가장 중요

파라미터화 쿼리(Prepared Statement)는 SQL의 구조를 먼저 DB에 보내 고정하고, 사용자 입력은 나중에 ?(또는 :name) 자리표시자에 값으로만 전달합니다. 입력이 아무리 ' OR 1=1 -- 같아도 DB는 그것을 하나의 문자열 값으로만 취급하므로 문법으로 해석되지 않습니다. 거의 모든 SQL 인젝션을 원천 차단하는 1차 방어입니다.

❌ 나쁜 예 — 문자열 결합 (Node.js)

db.prepare(
  `SELECT * FROM users
   WHERE username = '${username}'`
).all();

✅ 좋은 예 — 파라미터 바인딩 (Node.js)

db.prepare(
  `SELECT * FROM users
   WHERE username = ?`
).get(username);  // 값으로만 전달

언어별 파라미터화 예시

❌ Python — 문자열 포매팅

cur.execute(
  "SELECT * FROM users WHERE name='%s'" % name
)

✅ Python — 플레이스홀더

cur.execute(
  "SELECT * FROM users WHERE name = ?",
  (name,)            # 튜플로 바인딩
)

❌ Java — Statement + 결합

stmt.executeQuery(
  "SELECT * FROM users WHERE id='"+id+"'"
);

✅ Java — PreparedStatement

PreparedStatement ps = con.prepareStatement(
  "SELECT * FROM users WHERE id = ?");
ps.setString(1, id);
ps.executeQuery();

❌ PHP — 변수 삽입

$db->query(
  "SELECT * FROM users WHERE u='$u'"
);

✅ PHP — PDO Prepared

$st = $db->prepare(
  "SELECT * FROM users WHERE u = :u");
$st->execute([':u' => $u]);
⚠️
주의: 테이블명·컬럼명·ORDER BY 방향 같은 식별자는 ? 로 바인딩할 수 없습니다. 이런 값은 반드시 화이트리스트(허용된 목록 중 하나인지 확인)로 검증해야 합니다. → 7장 참고.

6. 방어② ORM 프레임워크 권장

Sequelize·Prisma·TypeORM·Django ORM·Hibernate 같은 ORM은 객체/메서드로 조건을 표현하면 내부적으로 파라미터화 쿼리를 자동 생성합니다. 개발자가 SQL을 손으로 결합할 일이 없어져 인젝션 위험이 구조적으로 줄고, 생산성도 높습니다. 이 사이트의 ORM 모드도 동일한 원리(값을 전부 ?에 바인딩)로 동작합니다.

✅ Sequelize (Node.js)

User.findOne({
  where: { username, password }
});
// → WHERE username = ? AND password = ?

✅ Prisma (Node.js)

prisma.user.findFirst({
  where: { username, password }
});
⚠️
ORM도 raw query 기능(sequelize.query("..."+input), $queryRawUnsafe 등)으로 직접 문자열을 결합하면 똑같이 취약해집니다. ORM을 쓰더라도 raw 쿼리에는 반드시 바인딩 파라미터를 사용하세요.

7. 방어③ 화이트리스트 입력 검증 보조

화이트리스트(allowlist)는 "허용된 것만 통과"시키는 방식입니다. 예를 들어 아이디는 영문·숫자·_ 1~32자만 허용하면, ' 나 -- 가 포함된 공격 입력은 입력 단계에서 거부됩니다. 금지 문자를 나열하는 블랙리스트보다 안전합니다(빠뜨린 문자가 없으므로).

const USERNAME = /^[A-Za-z0-9_]{1,32}$/;
if (!USERNAME.test(username)) return reject("형식 오류");  // 공격 입력 차단

특히 식별자(테이블·컬럼명), 정렬 방향, 페이지 크기처럼 파라미터화가 불가능한 값에는 화이트리스트가 필수입니다.

const SORT = { name: "name", date: "created_at" };
const col = SORT[req.query.sort] || "name";   // 허용된 컬럼만
db.prepare(`SELECT * FROM posts ORDER BY ${col}`);
🚧
화이트리스트 단독은 한계가 있습니다. 비밀번호·게시글 본문처럼 특수문자를 정상적으로 허용해야 하는 입력엔 적용이 어렵고, 검증 규칙의 빈틈으로 우회될 수 있습니다. 반드시 파라미터화 쿼리(5장)와 함께 쓰는 심층 방어(defense-in-depth)의 한 겹으로 사용하세요.

8. 보조 방어 — WAF (웹 방화벽) 보조

WAF(Web Application Firewall)는 애플리케이션 앞단에서 들어오는 요청을 검사해, 잘 알려진 공격 패턴(시그니처)을 코드에 도달하기 전에 차단합니다. ModSecurity, AWS WAF, Cloudflare 등이 대표적입니다. 이 사이트의 WAF 토글도 아래 같은 시그니처를 탐지합니다.

' OR / -- / UNION SELECT / ; DROP / SLEEP( / OR 1=1 ...

👍 장점

  • 코드 수정 없이 빠르게 1차 방어선 추가
  • 알려진 자동화 공격·스캐너를 대량 차단
  • 로깅·탐지로 공격 가시성 확보

👎 한계

  • 패턴 기반이라 인코딩·주석 삽입 등으로 우회 가능
  • 정상 입력을 막는 오탐(false positive)
  • 근본 원인(문자열 결합)은 그대로 — 임시방편
💡
WAF는 "시간을 벌어주는 울타리"입니다. 진짜 방어는 코드 레벨의 파라미터화 쿼리이며, WAF는 그 위에 더하는 보조막으로 보세요. 실습실에서 WAF를 켜고 페이로드를 변형해 우회되는지 직접 실험해볼 수 있습니다.

9. 추가 하드닝

  • DB 계정 최소 권한 — 애플리케이션 계정에 DROP·관리 권한을 주지 않으면 인젝션 피해 범위가 줄어듭니다.
  • 상세 오류 메시지 숨김 — 사용자에게는 일반화된 오류만 보여주고, 상세 로그는 서버 내부에만 남깁니다(오류 기반 공격 차단).
  • 비밀번호 해시 저장 — bcrypt/argon2로 해시하면, 설령 테이블이 유출돼도 평문 비밀번호가 바로 드러나지 않습니다. (이 더미 사이트는 피해를 보여주려 일부러 평문 저장)
  • 입력 길이·타입 제한 — 숫자 파라미터는 정수로 캐스팅, 과도한 길이 차단.
  • 정기 점검 — 정적 분석(SAST)·동적 스캐너로 결합 쿼리를 지속 탐지.

10. 무차별 대입(Brute Force) 방어

인젝션이 막혀도 공격자는 비밀번호를 반복 추측할 수 있습니다. 더미 사이트 로그인에서 틀린 비밀번호로 여러 번 시도하면 경고 → 위험 → 계정 잠금으로 단계가 올라가는 것을 볼 수 있습니다. 실무 방어책은 다음과 같습니다.

  • 속도 제한(Rate limiting) — IP/계정당 분당 시도 횟수 제한
  • 계정 잠금·지연 — N회 실패 시 일시 잠금, 실패할수록 응답 지연 증가
  • CAPTCHA — 자동화 도구 차단
  • 2단계 인증(2FA) — 비밀번호가 뚫려도 추가 인증으로 방어
  • 이상 로그인 알림 — 새 기기/지역 로그인 시 사용자에게 통지

🔓 내 비밀번호는 몇 번 만에, 몇 시간 만에 뚫릴까?

11. 최종 체크리스트

  • ✅ 모든 쿼리에 파라미터화/Prepared Statement 사용 (문자열 결합 금지)
  • ✅ ORM 사용 시에도 raw 쿼리에는 바인딩 적용
  • ✅ 식별자·정렬·페이지 값은 화이트리스트로 검증
  • ✅ 입력 검증(형식·길이·타입)을 추가 방어막으로 적용
  • ✅ WAF로 알려진 공격 시그니처 1차 차단 (단, 근본 방어 아님)
  • ✅ DB 계정 최소 권한, 상세 오류 메시지 숨김
  • ✅ 비밀번호 해시(bcrypt/argon2) 저장
  • ✅ 로그인 속도 제한·계정 잠금·2FA로 무차별 대입 방어
